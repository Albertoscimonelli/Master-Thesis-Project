 2. PIPELINE DI ESECUZIONE
================================================================================

Il progetto ha due stadi, eseguiti in sequenza:

  STADIO 1 - Python (CER_LoadProfiles/): genera i profili di carico annuali
  STADIO 2 - MATLAB (root): analizza energia, ricavi, ripartizione CER, e
             dimensiona l'impianto PV

--------------------------------------------------------------------------------
 2.1  Stadio Python
--------------------------------------------------------------------------------

    cd CER_LoadProfiles
    python generate_load_profiles.py

    +----------------------------+
    |  simulation_config.yaml    |  <-- Configurazione
    +----------------------------+
                |
                v
    +----------------------------+
    |  generate_load_profiles.py |  <-- Orchestratore
    +----------------------------+
          |              |
          v              v
    +------------+  +------------+
    | ramp_runner|  | lpg_runner |
    | (aziende)  |  | (famiglie) |
    +------------+  +------------+
    | Output:    |  | Output:    |
    | 1 min, W   |  | 1 min, W   |
    +------------+  +------------+
          |              |
          v              v
    +----------------------------+
    |    postprocessing.py       |
    | - Aggregazione oraria in   |
    |   energia (kWh per ora)    |
    | - Export CSV                |
    +----------------------------+
                |
                v
    +----------------------------+
    |   outputs/csv/             |
    |   4 file CSV (kWh/h, 2025) |
    +----------------------------+

La risoluzione di output e' fissa a 1 ora (energia in kWh per ora): non e'
piu' un parametro configurabile (vedi Sezione 6 per i dettagli storici).

================================================================================
 3. DESCRIZIONE DEI FILE PYTHON (CER_LoadProfiles/)
================================================================================

--------------------------------------------------------------------------------
 3.1  generate_load_profiles.py  (ENTRY POINT)
--------------------------------------------------------------------------------

SCOPO: Orchestrare l'intera pipeline di generazione profili.

COME FUNZIONA:
  1. Setup logging
  2. Parsing argomenti CLI (--config per file YAML personalizzato)
  3. Carica configurazione da YAML (load_config)
  4. FASE 1: run_ramp() genera i profili aziende (salta con warning se RAMP
     non e' installato)
  5. FASE 2: run_lpg() genera i profili famiglie (usa pyLPG se disponibile,
     altrimenti profili sintetici di fallback)
  6. Verifica che almeno un set di profili sia stato generato
  7. FASE 3: resample_to_hourly_energy() aggrega entrambi i DataFrame a
     energia oraria (kWh/h); rimuove timezone e duplicati nell'indice
  8. FASE 4: export CSV (profili_aziende, profili_famiglie, profili_tutti,
     profilo_CER_aggregato)
  9. Stampa riepilogo finale con statistiche

--------------------------------------------------------------------------------
 3.2  ramp_runner.py  (PROFILI AZIENDE)
--------------------------------------------------------------------------------

SCOPO: Generare profili di carico per utenze commerciali/industriali usando
       la libreria RAMP (rampdemand).

COME FUNZIONA:
  1. All'import, applica 2 patch di compatibilita':
     - _patch_ramp_numpy2(): corregge int(np.diff()) per NumPy >= 2.0
     - _patch_ramp_pandas3(): corregge alias "T" -> "min" per Pandas >= 3.0
  2. Per ogni use_case nel YAML (office, small_industry, retail), per ogni
     istanza configurata: seed deterministico, create_user(), genera
     profilo 1D in Watt a risoluzione 1 minuto (anno intero)
  3. Assembla tutti i profili in un DataFrame con DatetimeIndex

  NOTA SUI SEED: il seed e' calcolato come hash(f"{nome}_{indice}") % 2^31.
  In Python, hash() su stringhe e' salato per processo (PYTHONHASHSEED),
  quindi il seed NON e' identico tra esecuzioni diverse: i profili RAMP
  non sono bit-per-bit riproducibili da un run all'altro. Per ottenere
  seed davvero deterministici servirebbe una funzione hash non salata
  (es. zlib.crc32) al posto di hash().

--------------------------------------------------------------------------------
 3.3  lpg_runner.py  (PROFILI FAMIGLIE)
--------------------------------------------------------------------------------

SCOPO: Generare profili di carico per famiglie residenziali usando pyLPG.
       Se pyLPG non e' disponibile, genera profili sintetici di fallback
       basati su pattern italiani (pensionati, coppie lavoratrici, famiglie
       con figli).

  Generazione sempre a 1 minuto (costante _GENERATION_RESOLUTION_MINUTES,
  non configurabile): il postprocessing aggrega poi a 1 ora.

--------------------------------------------------------------------------------
 3.4  postprocessing.py  (AGGREGAZIONE ED EXPORT)
--------------------------------------------------------------------------------

FUNZIONI:

  resample_to_hourly_energy(df)
    - Input: DataFrame 1-min in Watt
    - Aggrega ogni ora: E[kWh] = mean(P[W]) * 1h / 1000
    - Output: DataFrame orario in kWh per ora

  aggregate_profiles(dfs)
    - Somma tutte le colonne di tutti i DataFrame (gia' in kWh/h)
    - Output: DataFrame con colonna "total_CER_kWh"

  export_to_csv(df, filepath, convert_w_to_kw, add_kwh_suffix)
    - Timestamp ISO8601, separatore virgola, 3 cifre decimali
    - Compatibile con MATLAB readtable()

--------------------------------------------------------------------------------
 3.5  config/simulation_config.yaml  (CONFIGURAZIONE)
--------------------------------------------------------------------------------

SEZIONI:

  simulation:
    year: 2025                        Anno di simulazione
    timezone: "Europe/Rome"           Fuso orario per RAMP
    (la risoluzione di output e' fissa a 1 ora, non configurabile)

  ramp:
    date_start / date_end             Periodo di simulazione
    use_cases: [office, small_industry, retail]   con num_users ciascuno

  lpg:
    households: [pensionati, coppia_lavoratori, famiglia_1figlio]  con count
    house_type / energy_intensity

  output:
    folder: "outputs/csv"
    aggregate_total / individual_profiles

--------------------------------------------------------------------------------
 3.6-3.8  ramp_inputs/use_cases/{office,small_industry,retail}.py
--------------------------------------------------------------------------------

Definiscono gli elettrodomestici (nome, numero, potenza, ore di
funzionamento, finestra oraria) di un ufficio, una piccola industria e un
negozio al dettaglio italiani tipici. Vedi i docstring dei singoli file
per il dettaglio orario di ciascun carico.

--------------------------------------------------------------------------------
 3.9  lpg_inputs/household_definitions.py  (CATALOGO FAMIGLIE)
--------------------------------------------------------------------------------

File di riferimento (non importato dal codice, la config e' nel YAML) con
il catalogo dei template pyLPG usati: pensionati (CHR54), coppia
lavoratori (CHR02), famiglia con 1 figlio (CHR03).


================================================================================
 4. DESCRIZIONE DEI FILE MATLAB (root)
================================================================================

--------------------------------------------------------------------------------
 4.1  MAIN.m  (ENTRY POINT - analisi energetica ed economica)
--------------------------------------------------------------------------------

Pipeline a sezioni indipendenti:
  0) Configurazione (percorsi, costanti, parametri economici)
  1) Caricamento profili di carico + generazione PV; assegnazione degli
     impianti PV ai proprietari con autoconsumo (vedi Sezione 7)
  2) Energia condivisa/venduta (al netto dell'autoconsumo del proprietario)
  3) Analisi economica (ricavi mensili/annuali)
  3b/3c) Ripartizione dell'incentivo CER: Shapley value e Nucleolo
  4) Costo energia da rete (PUN 2025) per utente e modalita' tariffaria
  5) Visualizzazione (istogrammi, profili stagionali, confronti)

--------------------------------------------------------------------------------
 4.2  cer_coalition_values.m, shapley_cer.m, nucleolus_cer.m
--------------------------------------------------------------------------------

Modello di gioco cooperativo a utilita' trasferibile per ripartire
l'incentivo sull'energia condivisa tra PV (produttore) e consumatori.

  cer_coalition_values.m   Costruisce v(S) per OGNI coalizione (2^n),
                            condivisa da entrambi i metodi di riparto cosi'
                            che siano direttamente confrontabili.
  shapley_cer.m             Shapley value in forma esatta (Moncecchi et al.,
                            Appl. Sci. 2020, eq. 39).
  nucleolus_cer.m            Nucleolo via sequenza di LP (Fioriti et al.,
                            Appl. Energy 2021, eq. 7); se il Core e'
                            non-vuoto il Nucleolo vi appartiene ed e'
                            quindi stabile. Se il sistema di vincoli non
                            raggiunge rango pieno, la funzione emette un
                            warning ('nucleolus_cer:notUnique') perche' il
                            risultato potrebbe non essere l'unico punto
                            del nucleolo.

Per la derivazione matematica completa vedi GUIDA_modelli_distribuzione.md.

--------------------------------------------------------------------------------
 4.3  profilo_prezzi_pun_2025.m
--------------------------------------------------------------------------------

Genera il profilo orario dei prezzi PUN 2025 per 3 modalita' tariffarie
(MONORARIA, BIORARIA, ORARIO_VARIABILE), con calendario festivi italiani
2025 e fasce orarie ARERA (F1/F2/F3).

--------------------------------------------------------------------------------
 4.4  irr_bisection.m
--------------------------------------------------------------------------------

Calcola l'Internal Rate of Return per bisezione, senza dipendere dalla
Financial Toolbox (la funzione irr() nativa di MATLAB la richiede).
Usata da optimizer_PV.m e PROVA_PV.m al posto di irr(). Assume un solo
cambio di segno nel flusso di cassa; ritorna NaN se non trova una radice
nell'intervallo di tassi esplorato [-99%, 1000%].

--------------------------------------------------------------------------------
 4.5  optimizer_PV.m  (dimensionamento impianto PV)
--------------------------------------------------------------------------------

Ottimizzazione di un impianto fotovoltaico su copertura industriale.
Loop su 3 variabili decisionali (numero di inverter, tilt, distanza
inter-fila): per ogni combinazione calcola layout fisico, fattibilita'
elettrica, simulazione oraria annuale (posizione solare, ombreggiamento,
produzione DC/AC, bilancio energetico) e analisi economica (CAPEX, OPEX,
ricavi, IRR, NPV). Seleziona la configurazione ottimale e produce grafici
3D dello spazio delle soluzioni.

--------------------------------------------------------------------------------
 4.6  PROVA_PV.m  [LEGACY]
--------------------------------------------------------------------------------

Versione precedente di optimizer_PV.m, mantenuta come riferimento
storico. Presenta alcune semplificazioni superate nella versione attuale
(NPV non attualizzato, irradianza non clampata, profilo di consumo
giornaliero fisso invece che annuale da CSV). Non e' piu' il percorso di
esecuzione consigliato.


================================================================================
 5. FORMATO DEI CSV DI OUTPUT (CER_LoadProfiles/outputs/csv/)
================================================================================

Tutti i CSV hanno lo stesso formato, compatibile con MATLAB readtable():

  - Separatore: virgola (,)
  - Prima colonna: timestamp in formato ISO8601 (YYYY-MM-DDTHH:MM:SS)
  - Valori: energia in kWh consumata in quell'ora (colonne con suffisso _kWh)
  - Risoluzione temporale: 1 ora
  - Periodo: anno 2025
  - Numero righe: ~8760 (una per ora dell'anno)

DETTAGLIO FILE (con la configurazione di default: 1 office, 1 small_industry,
1 retail, 3 famiglie):

  profili_aziende.csv     colonne: timestamp, office_1_kWh,
                          small_industry_1_kWh, retail_1_kWh
  profili_famiglie.csv    colonne: timestamp, household_1_kWh,
                          household_2_kWh, household_3_kWh
  profili_tutti.csv       timestamp + tutte le colonne aziende e famiglie
                          (join sui timestamp comuni)
  profilo_CER_aggregato.csv   colonne: timestamp, total_CER_kWh

NOTA: i profili RAMP sono generati su indice tz-aware (Europe/Rome) e poi
privati del timezone; questo puo' causare la perdita/duplicazione delle
ore di cambio ora legale (fine marzo / fine ottobre) rispetto ai profili
LPG, generati tz-naive. MAIN.m interpola linearmente l'eventuale ora
mancante tramite retime() sulla griglia oraria canonica.

 6. COMPATIBILITA' E PATCH
================================================================================

Il progetto usa versioni recenti delle librerie (numpy 2.x, pandas 3.x,
rampdemand 0.5.0). RAMP 0.5.0 non e' ancora aggiornato per queste
versioni: ramp_runner.py applica 2 patch automatiche a runtime (vedi
Sezione 3.2). Sono temporanee e potranno essere rimosse quando RAMP
rilascera' una versione nativamente compatibile.

I due file requirements.txt hanno scopi diversi mantenuti allineati:
  - requirements.txt (root)              freeze completo dell'ambiente
                                          Python effettivamente usato
                                          (numpy==2.4.4, pandas==3.0.2, ...)
  - CER_LoadProfiles/requirements.txt     dipendenze dirette del pacchetto,
                                          con range di versione coerenti
                                          con le patch sopra (numpy>=2.0,
                                          pandas>=3.0)

 7. MODELLO DI AUTOCONSUMO E ASSEGNAZIONE DEGLI IMPIANTI PV (MAIN.m §1b)
================================================================================

Ogni impianto PV e' fisicamente "dietro al contatore" di UN giocatore
della comunita' (il proprietario): la sua produzione copre PRIMA
l'autoconsumo del proprietario, e SOLO l'eccedenza e' disponibile per la
condivisione con il resto della comunita'. Questa e' la stessa priorita'
usata in optimizer_PV.m (1: autoconsumo edificio, 2: CER, 3: rete), ed e'
piu' corretta del modello precedente (in cui l'intera produzione PV era
condivisa con l'intera domanda della comunita', senza distinguere
l'autoconsumo del proprietario).

CONFIGURAZIONE ATTUALE: un solo impianto (PV_Generation/Salvaplast_*.CSV),
assegnato al giocatore "small_industry_1_kWh".

STRUTTURA DATI (in MAIN.m):

  pvPlants = struct( ...
      'file',  {pvFile}, ...
      'owner', {"small_industry_1_kWh"});

Per ogni impianto in pvPlants:
  1. Si carica la produzione oraria genPV_p (kWh/h)
  2. selfCons_p = min(genPV_p, carico_proprietario)   (autoconsumo fisico)
  3. surplus_p  = max(0, genPV_p - carico_proprietario)   (va alla CER)
  4. Il carico del proprietario usato nel gioco/nel bilancio CER viene
     sostituito dal carico RESIDUO: max(0, carico_proprietario - genPV_p)

genPVSurplus (somma di tutti i surplus_p) e loadForShare (carichi con i
proprietari ridotti al residuo) sono poi usati sia per il bilancio
condivisa/venduta (§2) sia come input del gioco cooperativo Shapley/
Nucleolo (§3b/3c), cosi' l'energia gia' autoconsumata non viene mai
contata due volte.

ESTENSIONE FUTURA A PIU' IMPIANTI: per assegnare piu' impianti PV a
giocatori diversi (es. 4 impianti residenziali + 1 industriale) basta
estendere i due cell array di pvPlants, senza modificare il resto del
codice:

  pvPlants = struct( ...
      'file',  {pvFile_h1, pvFile_h2, pvFile_h3, pvFile_h4, pvFile_ind}, ...
      'owner', {"household_1_kWh", "household_2_kWh", "household_3_kWh", ...
                "household_4_kWh", "small_industry_1_kWh"});

Se un giocatore ha piu' impianti, il carico residuo viene ridotto in modo
incrementale (impianto per impianto) cosi' i contributi si sommano
correttamente in autoconsumo.


================================================================================
 8. COME MODIFICARE LA SIMULAZIONE
================================================================================

CAMBIARE ANNO:
  -> Modifica simulation_config.yaml: simulation.year (e ramp.date_start/
     date_end); aggiorna ANNO in MAIN.m e profilo_prezzi_pun_2025.m di
     conseguenza (i prezzi PUN sono specifici del 2025).

AGGIUNGERE UN UFFICIO IN PIU':
  -> In simulation_config.yaml, aumenta num_users sotto "office"

AGGIUNGERE UN NUOVO TIPO DI AZIENDA (es. ristorante):
  1. Crea ramp_inputs/use_cases/restaurant.py con create_user()
  2. Aggiungi la voce in simulation_config.yaml sotto ramp.use_cases

AGGIUNGERE FAMIGLIE:
  -> Cambia "count" nel YAML, oppure aggiungi un nuovo gruppo con un
     template pyLPG diverso

ASSEGNARE PIU' IMPIANTI PV A PIU' PROPRIETARI:
  -> Estendi la struct pvPlants in MAIN.m §1b (vedi Sezione 7)

CAMBIARE LA COMPOSIZIONE DEL QUARTIERE:
  -> Modifica SOLO simulation_config.yaml; non serve toccare il codice
     Python
